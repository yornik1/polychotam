# Walkthrough

## Триггер

Явные команды: `walkthrough <модуль>`, `tour <файл>`, `разбери <модуль>`, `пройдись по <модуль>`.

Без команды — также включается, если пользователь пишет «объясни», «разбери», «как работает», «не понимаю что тут», «что тут происходит» (см. `## Teach mode` в `CLAUDE.md`, маппинг намерений).

## Зачем (отличие от `quiz`)

- `quiz` — Socratic режим, спрашивает первым. Полезен **после** того, как примерно представляешь модуль.
- `walkthrough` — explainer-режим, объясняет первым, **без вопросов**. Нужен **до** quiz, когда модуль открыт впервые.
- Естественная пара: `walkthrough <модуль>` → `quiz <тот же модуль>`.

## Сценарий

### 1. Прочитать вход

- Если запрос — модуль (`walkthrough polymarket`): прочитать `src/<module>/<module>.module.ts` и все провайдеры/контроллеры из `providers/imports/exports`.
- Если запрос — файл (`walkthrough src/queue/trade-enrichment.processor.ts`): прочитать сам файл и **только** его прямые зависимости (импорты).
- Если модуль > 500 строк суммарно — **не читать всё**, предложить пользователю выбрать поддиректорию или конкретный сервис.

### 2. Дать карту

Один короткий блок:

- Какие классы / сервисы / контроллеры / процессоры в модуле.
- Кто кого зовёт (короткий список «A → B → C»).
- Какие провайдеры **экспортируются** (видны в других модулях) и зачем.
- Какие entity / DTO / контракты используются (по ссылкам на `src/types/contracts.ts` и `*.entity.ts`).

Цель — за 30 секунд чтения дать пользователю общее представление без деталей.

### 3. Пройтись сверху вниз по ключевым кускам

Для каждого ключевого куска:

- **CODE REFERENCE** на конкретные строки в формате ``` startLine:endLine:filepath ```.
- 3–5 предложений в обучающем формате:
  - Что делает.
  - Какой NestJS / TypeScript / TypeORM / BullMQ паттерн использован.
  - Зачем именно так (какую проблему решает).
  - Что было бы плохой альтернативой и почему.
- **Никаких вопросов** в этом блоке. Только разбор.

Что считать «ключевым куском»:

- Декораторы класса (`@Injectable`, `@Controller`, `@Processor`, `@Update`).
- Конструктор и DI (что инжектится и почему).
- Lifecycle-хуки (`onModuleInit`, `onApplicationBootstrap`).
- Публичные методы сервиса.
- Обработчики (`@Process`, `@Get`, `@On`).
- Нестандартные/неочевидные места (catch без re-throw, ручная запись в NDJSON, retry-логика и т.п.).

### 4. Связи с остальным проектом

В конце — 1–2 фразы: «Этот модуль **импортирует** из …, **экспортирует** для …, через очередь общается с …». Без подробностей, только верхний уровень.

### 5. Предложение перейти в `quiz`

Финальная строка:

> «Хочешь `quiz <тот же модуль>` для проверки понимания, продолжить с другим модулем или копнуть в конкретный файл глубже?»

## Правила

- **Никаких правок кода.** Только чтение и объяснение.
- **Никаких вопросов** на проверку понимания внутри сценария — только в самом конце предложение перейти в `quiz`.
- Опираться на **реальные** пути / имена / сигнатуры из репозитория. Никаких абстрактных примеров.
- Если в коде есть очевидный bad smell или баг — **отметить** одной строкой, но **не править** (это вне скилла; предложить `debug` / `fix`, если хочется чинить).
- Комментарии и обучающий текст — на русском, code terms и identifiers — на английском.
- Если модуль большой — разбить на 2–3 сообщения, спросить «продолжать?» **только** между сообщениями, не внутри сценария.

## Рекомендуемая последовательность для онбординга по проекту

Для нового изучения проекта (если пользователь просит «с чего начать») — порядок такой:

1. `walkthrough common` — общие утилиты, понять базу.
2. `walkthrough markets` — самый простой доменный модуль, видна связка entity ↔ TypeORM ↔ controller.
3. `walkthrough queue` — BullMQ-процессоры, NDJSON-логирование.
4. `walkthrough polymarket` — самый большой модуль (WS + REST + Gamma + backfill). Разбивать на части.
5. `walkthrough trades` + `walkthrough wallets` — обработка сделок и агрегаты.
6. `walkthrough telegram` — алерты, дедуп, форматтер.
