# Markets Ingest MVP Design (A)

## Контекст и цель

Цель первого вертикального среза: реализовать `GET /markets`, который отдает срез маркетов из одного вызова Polymarket без сохранения в БД.

Результат шага должен дать стабильный внешний контракт для клиентов и корректные границы между доменным модулем `markets` и интеграционным модулем `polymarket`.

## Границы и архитектура

- `MarketsController` предоставляет endpoint `GET /markets`.
- `MarketsService` инкапсулирует бизнес-логику получения и нормализации данных.
- `PolymarketHttpClient` (в `polymarket`) отвечает только за HTTP-доступ к upstream API.
- `MarketsModule` зависит от `PolymarketModule`, но не знает деталей URL/HTTP-конфигурации.

Принцип: наружу возвращается наш DTO-контракт, а не сырой payload Polymarket.

## DTO-контракт (`MarketDto`)

Минимальный контракт для MVP:

- `id: string`
- `slug: string`
- `question: string`
- `outcomes: string[]`
- `active: boolean`
- `closed: boolean`
- `liquidity: number`
- `volume24h: number`
- `endDate: string | null` (ISO-8601 строка или `null`)

Порядок элементов в `data` — как приходит из upstream (без дополнительной сортировки в MVP).

## Поток данных

1. Клиент вызывает `GET /markets`.
2. Контроллер делегирует обработку в `MarketsService.getMarkets()`.
3. Сервис запрашивает данные через `PolymarketHttpClient`.
4. Сервис преобразует upstream-данные в `MarketDto[]`.
5. Сервис возвращает ответ:

```json
{
  "data": [],
  "meta": {
    "source": "polymarket",
    "total": 0,
    "fetchedAt": "2026-04-01T00:00:00.000Z"
  }
}
```

`data` содержит срез записей из одного вызова upstream-эндпоинта. В MVP не реализуется обход страниц/курсорной пагинации: если upstream в этом вызове вернул усеченный набор, API возвращает его как есть, без гарантии полноты.

## Ошибки и наблюдаемость

- При недоступности upstream, таймауте, ответе `5xx` или `429` — возвращается `503 Service Unavailable`.
- Для остальных upstream `4xx` — возвращается `502 Bad Gateway`.
- При невалидном payload upstream — также `503`, без утечки внутренних деталей клиенту.
- Обоснование: невалидный payload трактуется как временная деградация upstream, чтобы сохранить единый клиентский паттерн ретраев в MVP.
- Логирование выполняется через `Logger` NestJS:
  - `log` на старте и успешном завершении загрузки (включая количество элементов),
  - `warn/error` при ошибках upstream.
- Для внешнего запроса задается явный таймаут (ориентир: 8-10 секунд).

## Тестовая стратегия

### Unit (`MarketsService`)

- Успешный сценарий: корректный маппинг upstream данных в `MarketDto[]`.
- Контрактный сценарий: проверка всех полей `MarketDto` и их типов.
- Проверка корректного формирования `meta.total`.
- Проверка маппинга ошибок: `429/5xx/timeout -> 503`, остальные `4xx -> 502`.

### Controller test

- `GET /markets` возвращает `200` и контракт `{ data, meta }` в успешном сценарии.
- Негативные сценарии: `503` при `429/5xx/timeout`, `502` при прочих `4xx`.

### Smoke/E2E минимум

- Endpoint доступен в поднятом приложении и возвращает ожидаемую структуру.

## Критерии готовности (Definition of Done)

- Реализован `GET /markets`, возвращающий срез из одного запроса к upstream Polymarket (без обхода страниц и без гарантии полноты).
- Внешний ответ стабилен и основан на внутреннем DTO-контракте.
- Ошибки upstream обрабатываются по карте: `429/5xx/timeout -> 503`, прочие `4xx -> 502`.
- Базовые unit/controller проверки добавлены и проходят.

## Что не входит в этот шаг

- Персистенс маркетов в PostgreSQL.
- Фоновые sync-задачи через BullMQ.
- Кэширование ответов.
- Пагинация/фильтрация/сортировка API.
