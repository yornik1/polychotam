# Polymarket CLOB WebSocket — дизайн

## Цель

Подключать NestJS-сервис к Polymarket CLOB по WebSocket: при старте видно в логах успешное подключение; при обрыве сети — автоматическое переподключение; входящие сообщения логируются; события сделок разбираются в строго типизированную модель и логируются построчно (кошелёк, сумма, маркет и пр.). Очереди и БД в рамках этой фичи **не** используются — только логирование.

## Объём (in scope)

- Исходящий WS-клиент к URL из конфигурации (`POLYMARKET_WS_URL`, `ConfigService.getOrThrow`).
- Выбор **топ-20 маркетов по объёму за 24ч** из того же источника, что уже есть в проекте: ответ `PolymarketHttpClient.fetchMarkets()`, поле `volume24hr`, сортировка по убыванию; в подписку передаются идентификаторы в формате, который требует официальный WS Polymarket CLOB (при расхождении документации и факта — ориентир на рабочий payload и фиксация в комментарии/спеке после проверки).
- Файл **`trade-event.ts`**: описание **одной** распознанной сделки (кошелёк, сумма, сторона, цена, маркет/актив, время и т.д. по фактическому payload). В этом файле **не** использовать тип `unknown` для полей сделки.
- Парсинг входящих сообщений: из сырого тела извлекаются записи с типом сделки (например `event_type === "trade"` — уточняется по реальному API); для остальных — без сборки `TradeEvent`.
- Логи только через **NestJS `Logger`**, без `console.log`.
- Переподключение с задержкой (например 5 с) после `close` / ошибки соединения; при **плановом** завершении модуля переподключение отключается.

## Вне объёма (out of scope)

- Запись сделок в PostgreSQL, публикация в BullMQ, вызов `TradesModule`.
- E2E-тест против живого Polymarket по сети (допустимы unit-тесты парсера и чистых функций).
- Отдельный env для backoff (допустима константа в коде в MVP; при необходимости позже — `POLYMARKET_WS_RECONNECT_MS`).

## Архитектура

**Рекомендуемый вариант:** отдельный провайдер **исходящего** WS-клиента (например `PolymarketWsClient` / `PolymarketClobWsService`) в модуле `polymarket`. Не использовать `@WebSocketGateway` для соединения с Polymarket — gateway предназначен для входящих клиентов к приложению.

**Компоненты:**

| Компонент | Ответственность |
|-----------|-----------------|
| `trade-event.ts` | Типы/интерфейс одной сделки без `unknown` в полях сделки |
| Парсер (функция или маленький класс) | Сырой JSON → `TradeEvent` или «не сделка»; без выброса необработанных исключений наружу процесса |
| WS-клиент | Жизненный цикл `ws`, загрузка топ-20, подписка, лог сырья, вызов парсера, лог по сделке, reconnect |

**Поток данных:** старт модуля → HTTP `fetchMarkets` → сортировка и срез топ-20 → `WebSocket` connect → сообщение подписки → на `message`: лог сырого тела (например `debug`) → парсинг → для сделок `log` с кошельком, суммой, маркетом (и пр. по ТЗ).

## Ошибки и устойчивость

- Сбой HTTP при получении маркетов: лог, backoff, повтор всего цикла (без tight loop).
- Невалидный JSON / неожиданная структура: `warn`, процесс не падает.
- `error` / `close` на сокете: закрытие, планирование reconnect; при `onModuleDestroy` — флаг завершения, без повторных подключений.

## Конфигурация

- `POLYMARKET_WS_URL` — обязательно через `ConfigService`.
- Значение по умолчанию в `.env.example` согласовать с рабочим endpoint CLOB (как в проекте сейчас).

## Тестирование

- Unit-тесты парсера: фикстуры → ожидаемый `TradeEvent` или отсутствие сделки.
- По возможности: чистая функция выбора топ-20 из массива сырых маркетов — отдельный тест без сети.

## Критерии готовности

- При запуске сервиса в логах есть явное сообщение об успешном подключении WS.
- При имитации обрыва соединения клиент снова подключается без ручного рестарта.
- В логах видны сырые входящие сообщения (на выбранном уровне) и отдельные строки по каждой распознанной сделке (кошелёк, сумма, маркет).
- Проект собирается без ошибок TypeScript; в `trade-event.ts` нет `unknown` для полей сделки; в коде фичи нет `console.log`.
